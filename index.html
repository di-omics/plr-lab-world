Reverse engineering the hall

9 stations. For each one: is it already decoded, how does software reach it, and what does a first run look like.

Every run on this page is a simulation. Nothing here ran on a physical instrument. Built against the public PyLabRobot source at commit 182f92e of 23 Nov 2026.

TODO_1, TODO_2 and so on are placeholders used on purpose: each marks a payload not yet decoded or a fact about the real instrument not yet known.

Watch each station run in simulation

The method is the same at every station

  1. Ask first: is it already decoded? Read the PyLabRobot device registry and source before touching the instrument. 3 of these 9 stations already are.
  2. If the maker publishes an interface, use it. An SDK means there is nothing to decode. Write 1 small class around it.
  3. If not, extract, don't guess. Capture the maker's own software doing 1 action at a time. Get the wire format exact: transport, framing, checksum, handshake.
  4. Write 1 plain class. Its public methods state intent and are safe to repeat: read the state, act only if needed, confirm.
  5. Prove it without the instrument. Replay the traffic against the class. Errors keep their code. An unverified driver says so when it starts.
  6. The first live command only reads. Then 1 move with empty labware and a person present.

Steps 3 to 5 follow the PyLabRobot device driver guide. Steps 3 and 6 follow my reverse engineering playbook.

Station 1 of 9 / Instrument not chosen yet

Tissue-culture station

Supplier and interface are still open, so there is no protocol to show yet.

How software reaches it
Not decided. The example uses a made-up stand-in: 1 JSON message per release, the adapter speaks first, the station acknowledges or refuses. A real adapter would wrap what the chosen supplier documents.
Where the commands came from
Nothing decoded and nothing to decode yet. The message format, the error name unknown_batch and the ids are invented for this stand-in (TODO_1: the real interface). The questions below come from the toolkit's APPROACH.md and PREFLIGHT.md.

Decide it

  1. Does it have an external serial, USB or Ethernet port, so a teardown can be skipped? (APPROACH.md:19-20)
  2. Does the vendor PC app drive it over a link you can mirror and capture, 1 setpoint at a time? (APPROACH.md:71-82)
  3. Is there a Ready, Start and Stop remote connector you could use as a minimal first tier? (APPROACH.md:22-43)
  4. Which commands are read-only telemetry and which actuate, so you can arm them separately? (APPROACH.md:3-6 and APPROACH.md:45-51)
  5. Can your software be the sole master with the vendor app closed? (APPROACH.md:92-93)
  6. Which limits and interlocks stay on the instrument, and can you stay out of its internals? (APPROACH.md:5-6 and PREFLIGHT.md:7-8)

The example

Release 1 cell batch for seeding and check that the receiving worklist names that batch in every row. Batch and worklist ids are made up.

Station 2 of 9 / Decoded, in PyLabRobot

Agilent BioTek EL406

In PyLabRobot, v1 class EL406, registry status mostly (devices.json:120-122). Binary frames over FTDI USB.

How software reaches it
FTDI USB, 38400 baud 8N2, no flow control. Host speaks first: 11-byte header (cmd, length, checksum), payload (protocol.py:15-25). Reply: ACK 0x06, header, data (el406.py:318-319). Steps polled by 0x92 (el406.py:595).
Where the commands came from
The v1 code names no source for the protocol. Legacy wash tests check bytes against reference captures from real EL406 hardware (steps_wash_tests.py:570-571). Some limits are labelled as the vendor GUI's (peristaltic_dispenser.py:176 and el406.py:1015-1018).

Drive the real one

  1. Connect the EL406 by USB. setup() opens it as an FTDI device at 38400 baud 8N2, no flow control (el406.py:147-157).
  2. Create EL406(name="el406", device_id=<FTDI serial>); the FTDI layer refuses to pick when several devices match (ftdi.py:601-606 and el406.py:84).
  3. await el406.setup(): it sends TEST_COMM 0x73, INIT_STATE 0xA0, then a full RESET 0x70 unless skip_reset=True (el406.py:178-186 and el406.py:290-303).
  4. el406.set_plate(plate) with the PLR plate really loaded: 96, 384 or 1536 wells only (el406.py:113-119 and helpers.py:67-74).
  5. In async with el406.batch(): peristaltic_dispenser.prime(volume=...), .dispense(volumes={col: uL}) (peristaltic_dispenser.py:83-94 and peristaltic_dispenser.py:139-145).
  6. await el406.stop(). Check the wells by eye and file the upstream device test report (needs-testing.md:31-35).

The example

Seed cells into a 384-well plate: set up, open a batch, prime the peristaltic lines with 500 uL, dispense 40 uL into every well (24 columns), close the batch. Made-up round volumes.

el406 = EL406(name="el406")
el406.io = sim  # the only swap: the FTDI transport becomes the simulator
tap.ask("set up: FTDI 38400 8N2, TEST_COMM, INIT_STATE, RESET")
await el406.setup()

plate = cellvis_384_wellplate_120uL_Fb(name="cells_384")
el406.set_plate(plate)
tap.ask("open a batch for the 384-well plate")
async with el406.batch():
  tap.ask("prime the peristaltic lines, 500 uL")
  await el406.peristaltic_dispenser.prime(volume=500)

  tap.ask("dispense 40 uL per well, columns 1-24")
  volumes = {column: 40 for column in range(1, 25)}  # uL per well, by column
  await el406.peristaltic_dispenser.dispense(volumes=volumes)
  tap.ask("close the batch: home motors, end-of-batch marker")
await el406.stop()

What is real, what is simulated, and the limits found in the source

Real

  • Upstream EL406 class and its peristaltic dispenser, unchanged
  • Every frame byte the driver writes, incl. the 0x8F dispense frame
  • Error code table and message for 0x1355

Simulated

  • The EL406: frame and checksum decoding, replies, poll states
  • Device state: plate type, prime volume, uL per column, steps
  • Faults: dropped dispense reply; error 0x1355 in place of the dispense

Not checked

  • Any physical EL406; nothing here ran on hardware
  • Real reply header bytes beyond length and command echo (TODO_1)
  • Real busy time and post-fault state of a step (TODO_2)

Limits found in the source

  • No tests for the v1 class: pylabrobot/agilent/biotek/el406/ has no *_tests.py; wire tests are legacy only, with a canned MockFTDI (mock_tests.py:72).
  • Replies are not checked: the driver reads only the length at header bytes 7-8 and ignores markers and checksum (el406.py:364-371).
  • batch() first sends 7 unnamed commands (0xBF ... 0x010A) and only logs a warning if they fail (el406.py:724-731).
  • Docstrings say the plate comes from the plate_holder (el406.py:682 and el406.py:1021), but only set_plate() sets it (el406.py:113-119).

Station 3 of 9 / Decoded, in PyLabRobot

Hamilton Microlab STAR

In PyLabRobot. The real STARDriver sends text firmware commands over USB.

How software reaches it
USB, VID 0x08AF, PID 0x8000 (master.py:81-82). The host speaks first: ASCII commands like C0TPid0117xp... Each reply repeats module, command and id, then er00/00 or an error code (framing.py:3-5 and framing.py:319-320).
Where the commands came from
Upstream does not say how the commands were first obtained. Its code cites the firmware docs (framing.py:38), marks some codes as observed, not documented (errors.py:349), and its debug page compares PLR commands with VENUS USB trace files (debug.md:7-11).

Drive the real one

  1. With Python 3.10 or newer, in a virtual environment: pip install "pylabrobot[usb]", which adds pyusb and libusb-package (installation.md:3 and installation.md:47).
  2. Connect the STAR by its USB cable. On macOS also install libusb (brew install libusb); on Linux the docs list nothing more (installation.md:90-100).
  3. On Windows, with no Hamilton or VENUS software running, use Zadig to give "ML Star" the libusbK driver; restore the original driver for VENUS (installation.md:108-144).
  4. STARDriver() with no io opens the USB device itself, VID 0x08AF, PID 0x8000 (master.py:145-152).
  5. Build the deck as it stands, then star = STARlet(deck=deck) or STAR(deck=deck). Setup refuses a deck whose track count differs from the device's (master.py:1155-1171).
  6. await star.setup() reads the device, then initializes it, so it moves (master.py:214). Then a first small step, such as picking up tips.

The example

Start-up conversation, then pick up 8 tips, aspirate 50 uL from column 1 of a source plate, dispense into column 1 of a destination plate, return the tips. Volumes made up.

def build(link):
  deck = STARLetDeck()
  tip_car = hamilton_tip_carrier_L5(name="tip_carrier")
  tip_car[0] = tips = hamilton_96_tiprack_300uL(name="tips")
  deck.assign_child_resource(tip_car, track=1)
  plt_car = hamilton_plate_carrier_L5_ac(name="plate_carrier")
  plt_car[0] = source = cor_96_wellplate_360uL_Fb(name="source")
  plt_car[1] = dest = cor_96_wellplate_360uL_Fb(name="destination")
  deck.assign_child_resource(plt_car, track=8)
  # On hardware: STARDriver() with no io opens the USB device itself.
  star = STARlet(deck=deck, driver=STARDriver(io=link))
  return star, tips, source, dest


async def sample_prep(star, tips, source, dest):
  await star.setup()
  await star.pipettes.pick_up_tips(tips["A1:H1"])

What is real, what is simulated, and the limits found in the source

Real

  • pylabrobot STARDriver, STARlet device and Pipettes feature, unchanged
  • Every frame the driver wrote: 274 commands; the log shows 7 kinds
  • Upstream liquid class: 50 uL asked goes out as av00551, 55.1 uL

Simulated

  • The USB transport, every reply and the reply router's clock (sim.py)
  • Device state: tips per channel, liquid per tip, volume per well
  • A cut-down STARlet: 8 channels, no iSWAP, 96-head or autoload

Not checked

  • Nothing ran on a physical STAR
  • Reply values and padding beyond the upstream recording and test captures
  • Timing, motion, real liquid behaviour and real error codes for this move

Limits found in the source

  • The device registry still points STAR at the legacy STARBackend, api v0 (devices.json:539-540).
  • Only the STAR recording was read off a device; the STARlet and STARplus ones are derived (README.md:5-7 and README.md:47).
  • 50 uL becomes 55.1 uL: the 400 uL tip maps to the 300 uL water class StandardVolume_Water_DispenseSurface_Part, curve 50.0: 55.1 (mapping.py:46 and mapping.py:14004-14010).
  • Upstream's own STARSimulationDriver answers above the wire: nothing reaches it (simulator.py:8), so wire replies here are this example's.

Station 4 of 9 / Decoded, in PyLabRobot, older interface

LiCONiC STX44 incubator

In PyLabRobot legacy only (v0); STX44_IC is a listed model (constants.py:5). ASCII over RS-232.

How software reaches it
RS-232, 9600 baud 8E1, RTS/CTS (liconic_backend.py:80-90). Host speaks first: a break, CR answered by CC, then 1 ASCII command per line (ST, RS, RD, WR DMn) ending in CR; replies end CR LF (liconic_backend.py:96-139).
Where the commands came from
Upstream points to LiCONiC documentation: tests check 2 reference points from the Liconic documentation (liconic_backend_tests.py:52-55), and a TODO says a shaker command must still be found there (liconic_backend.py:369). Many methods are marked UNTESTED (liconic_backend.py:365-554).

Drive the real one

  1. Connect the STX PLC by RS-232. The backend opens it at 9600 baud 8E1 with RTS/CTS (liconic_backend.py:80-90).
  2. Create ExperimentalLiconicBackend(model="STX44_IC", port="/dev/ttyUSB0"); models are listed in constants.py:5-63.
  3. Build Incubator(backend, racks=[...], ...) with liconic_rack_* racks matching the cassettes; cassette numbers follow the rack order (liconic_backend.py:141-147).
  4. await stx.setup(): break, CR -> CC, ST 1801 -> OK, then RD 1915 until 1 (liconic_backend.py:96-139).
  5. Put the plate on stx.loading_tray, then take_in_plate(site), fetch_plate_to_loading_tray(name), get_temperature() (incubator.py:111 and incubator.py:151-177).
  6. Watch the shovel by eye on the first runs and file the upstream device test report (needs-testing.md:31-35).

The example

Take 1 plate from the transfer station into cassette 1, position 1, fetch it back out to the transfer station, then read the temperature. Made-up slot and a made-up 37.0 deg C.

Station 5 of 9 / Maker's SDK, nothing to decode

Rail-mounted transfer arm (linear track)

Not in PyLabRobot yet, the maker's SDK documents it. The example writes the class.

How software reaches it
Through the xArm controller with xarm-python-sdk: the same XArmAPI object as the arm calls get/set_linear_motor_*; the SDK sends them as Modbus to the control box RS-485 (xarm-python-sdk xarm/x3/linear_motor.py:40-46).
Where the commands came from
Nothing decoded. Names, units and return codes come from xarm-python-sdk 1.18.4 (xarm-python-sdk xarm/wrapper/xarm_api.py:3648-3805, xarm-python-sdk xarm/x3/linear_motor.py:82-219, xarm-python-sdk xarm/x3/code.py:52-54). A search of PyLabRobot 182f92e for linear track or linear motor finds nothing.

Stand it up

  1. Read the track calls in the SDK: get_linear_motor_pos/status/error/on_zero/is_enabled and set_linear_motor_enable/back_origin/pos (xarm-python-sdk xarm/wrapper/xarm_api.py:3648-3805).
  2. Write 1 plain class with async setup() and stop(); stop() restores the enable state setup() found (device-driver-guide.md:22-23).
  3. Expose intent only: home() and move_to(mm) read the state, act only if needed, then confirm (device-driver-guide.md:39-41).
  4. Issue moves with wait=False and confirm in Python: error register, then motion bit 0 clear (xarm-python-sdk xarm/wrapper/xarm_api.py:3669-3670), then the position report.
  5. Log a warning in setup() that it is unverified (device-driver-guide.md:45-47); test it against a simulated SDK object first.
  6. Teach the station positions on the real track and set a measured reply timeout before any real run.

The example

Home the track if it is not homed, travel to a taught station at 450 mm and 200 mm/s, confirm the arrival from the position report. Positions and speed are made up.

async def travel(track: LinearTrack) -> int:
  await track.setup()  # enables the track if it was off
  await track.home()  # no-op when already homed

Station 6 of 9 / Maker's SDK, nothing to decode

UFACTORY xArm 6 plate arm

In PyLabRobot (XArm6). It wraps the maker's published Python SDK, so there is no wire to decode.

How software reaches it
Ethernet to the xArm controller through xarm-python-sdk (hello-world.ipynb:12). XArmAPI(ip) is created in setup(), then each operation is 1 blocking SDK call run in a thread (xarm6.py:86).
Where the commands came from
Nothing decoded. The driver calls the maker's SDK (xarm6.py:120-122) and checks only its return code (xarm6.py:60-95). The registry lists it as status basic (devices.json:2132).

Drive the real one

  1. Install the optional SDK extra: pip install PyLabRobot[xarm] (hello-world.ipynb:12).
  2. Create XArm6(ip=..., tcp_offset=...) with the controller IP and your gripper mount offset, then await setup().
  3. Teach the hotel and reader poses: start_freedrive_mode(free_axes=[0]), request_gripper_pose(), stop_freedrive_mode() (hello-world.ipynb:282).
  4. Open with move_gripper(width=max_gripper_width). The driver's default jaw range is 71 to 150 mm (xarm6.py:41-42): set it to your gripper.
  5. Wrap pick_up_at_location and drop_at_location with your own above-pose moves; they only move and grip (xarm6.py:270-271).
  6. Put a timeout around each call and check the plate yourself; the driver reports no plate-held state.

The example

Station 7 of 9 / Nothing to decode

Passive plate hotel

No controller, so nothing to decode. In PyLabRobot it is a resource: plate holders on a carrier.

How software reaches it
Nothing to reach: no wire. Software keeps a model of what sits on each shelf (PyLabRobot resources) and the arm that loads it is the only actor. The scheduler owns reservations and timers.
Where the commands came from
Nothing decoded. PyLabRobot 182f92e has no hotel class; the example uses a PlateCarrier (carrier.py:269-331) with 24 PlateHolder sites (carrier.py:159-211). Assigning to a taken spot raises ValueError (carrier.py:79-87).

Stand it up

  1. Measure the shelf pitch, the first shelf height and the plate seat; put them in a PlateCarrier of PlateHolder sites.
  2. Set pedestal_size_z for each PlateHolder; the constructor raises ValueError without it (carrier.py:184-189).
  3. Place with hotel[slot] = plate and remove with hotel[slot] = None, so a taken spot raises instead of stacking (carrier.py:104-111).
  4. Keep reservations and dwell timers in the scheduler, with a clock you can inject in tests.
  5. Free a slot only after the arm confirms the pickup; an unconfirmed pickup keeps the slot reserved.
  6. Teach the arm 1 pose per shelf and check each against the model before the first run.

The example

BMG LABTECH PHERAstar FSX

Not in PyLabRobot. Upstream drives 2 other BMG readers; this one's commands are unknown.

How software reaches it
Unknown. Upstream's 2 BMG readers share 1 framing module: the CLARIOstar speaks FTDI frames (STX, size, header, payload, 24-bit sum, CR) or USB packets, the VANTAstar USB only. The host asks, then polls status.
Where the commands came from
Nothing decoded. The example runs the method on a synthetic reader whose payloads are the text TODO_1..TODO_4. Upstream has no PHERAstar code; its registry lists only CLARIOstar and VANTAstar for BMG (devices.json:253-287).

Decode it

  1. Check how it enumerates on USB (FTDI bridge or native USB, VID and PID) against the 2 BMG readers upstream drives (framing.py:6 and framing.py:4).
  2. Capture the vendor software doing 1 action at a time (tray out, tray in, 1 read), marking each action, with plr-re capture and marks.
  3. Test the sibling framing on the capture: does every frame fit the FTDI frame or the USB packet layout (framing.py:3-17)?
  4. Map status and error replies before any motion: which bits mean busy, tray out, refused, error, and which codes come back.
  5. Write the 1-class driver and replay the captured transcripts as tests through a fake transport, per the device-driver guide section 5.
  6. First live command read-only (status), then the tray, then a read of an empty plate, with a person at the reader.
